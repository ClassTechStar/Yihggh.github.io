第七十六章：实战项目一——待办清单应用

理论全部到位，这一章咱们做一个完整的待办清单应用：输入待办、列表展示、标记完成、删除、本地持久化。功能不多，但它是"输入 → 状态 → 列表渲染 → 数据库"的完整闭环，和安卓篇的记账本、iOS 篇的第一个项目是同一个训练目的。

一、数据层：Model 与数据库封装

先把数据模型和数据库操作封装成独立文件（GoodTodo 项目的分层思想在这里同样适用）。模型字段先想清楚再动手：id / title / done 之外，以后想按时间排序就得有 createdAt，模型定得越清楚，后面加排序、筛选越不用大改：

ARKTS · model/TodoModel.ets···
import { relationalStore } from '@kit.ArkData'
import { Context } from '@kit.AbilityKit'

export interface Todo {
  id: number
  title: string
  done: boolean
}

export class TodoDb {
  private rdb: relationalStore.RdbStore | null = null

  async init(context: Context) {
    this.rdb = await relationalStore.getRdbStore(context, {
      name: 'todo.db',
      securityLevel: relationalStore.SecurityLevel.S1
    })
    await this.rdb.executeSql(
      'CREATE TABLE IF NOT EXISTS todo ' +
      '(id INTEGER PRIMARY KEY AUTOINCREMENT, title TEXT NOT NULL, done INTEGER DEFAULT 0)')
  }

  async list(): Promise<Todo[]> {
    let out: Todo[] = []
    let rs = await this.rdb?.querySql(
      'SELECT id, title, done FROM todo ORDER BY id DESC')
    while (rs?.goToNextRow()) {
      out.push({
        id: rs.getLong(rs.getColumnIndex('id')),
        title: rs.getString(rs.getColumnIndex('title')),
        done: rs.getLong(rs.getColumnIndex('done')) === 1
      })

分层的设计意图要说清楚：Todo 接口是"纯数据"（UI 层只认它），TodoDb 是"数据访问对象"（UI 层不直接碰 SQL）。这样的好处是：将来换存储方案（比如从 RelationalStore 换成 Preferences 存 JSON），只需要改 TodoDb 的实现，UI 层一行不动，第 37 章讲的"封装变化点"，在数据层同样成立。

模型设计还有个小坑提醒：done 字段用 INTEGER 存（SQLite 没有 boolean 类型），读出来时 === 1 转回 boolean，类型转换集中在 TodoDb 的读取方法里做，别让 UI 层知道"数据库里存的是 0 和 1"。封装的意义就是把"存储细节"挡在数据层之内。

二、UI 层：把列表页立起来

数据层就位，现在搭界面。先立一条规矩，整章都遵守：界面只读 @State，所有增删改都走数据层，改完库再整体回查刷新。

先立一条规矩。这条"单一数据源"原则看着啰嗦，实际能挡掉本章大部分 bug，后面"常见 bug 门诊"里翻车的例子，一大半都是违反了它。第 73 章讲过的组件在这一章全要用上：Column、Row、List、ForEach、TextInput、Checkbox，没有新面孔，功夫全在"拼"上。

页面骨架三步走：aboutToAppear 里初始化数据库（这是第 74 章讲过的生命周期标准位置），初始化完成后回查一次列表，build 里用 List 加 ForEach 渲染。注意拿 Context 的写法：全局 getContext 从 API 18 起已废弃，统一用 this.getUIContext().getHostContext()——底稿代码里已经是这么写的，你自己的项目也照这个来。先看全貌：

ARKTS · pages/Index.ets（列表页骨架）···
import { Todo, TodoDb } from '../model/TodoModel'

@Entry
@Component
struct TodoPage {
  @State todos: Todo[] = []
  @State input: string = ''
  private db: TodoDb = new TodoDb()

  aboutToAppear() {
    this.db.init(this.getUIContext().getHostContext()).then(async () => {
      this.todos = await this.db.list()
    })
  }

  build() {
    Column() {
      List({ space: 8 }) {
        ForEach(this.todos, (t: Todo) => {
          ListItem() {
            Row() {
              Checkbox().select(t.done)
                .onChange((v: boolean) => {
                  this.db.toggle(t.id, v).then(async () => {
                    this.todos = await this.db.list()
                  })
                })
              Text(t.title)
                .decoration({
                  type: t.done ? TextDecorationType.LineThrough
                               : TextDecorationType.None
                })
                .layoutWeight(1)
            }
            .width('100%').padding(12)
          }
        }, (t: Todo) => t.id.toString())
      }
      .layoutWeight(1)
    }
    .height('100%')
  }
}

这段代码跑起来就是一个能用的列表页：数据库里有什么，屏幕上就有什么；勾一下，数据库翻转状态，屏幕跟着画删除线。别急着往下滑，先把它拆成四块细看：键生成器、空状态、勾选交互、滑动删除，每一块都有新手必踩的坑。

键生成器：ForEach 的第三个人参，最不能省

ForEach 有三个参数：数据源、渲染函数、键生成器。前两个好理解，第三个经常被新手当成可有可无的尾巴直接省掉。它是列表更新的命脉：框架靠每个条目的"键"来判断哪些行是新的、哪些行变了、哪些行该删。键稳，更新就精准，diff 就小，动画也顺；键乱，轻则多刷新，重则删错行。

两个反面教材都真实常见。第一个是用索引当键：(t: Todo, idx: number) => idx.toString()——删掉中间一条后，后面所有条目的索引全部前移，框架以为"最后几行是新数据"，整片重建，勾选状态和动画跟着错位。第二个是用标题当键：t.title——你只要允许两条同名待办，键就撞了，框架的行为立刻不可预测。正确做法只有一种：用数据库主键，(t: Todo) => t.id.toString()。id 唯一、稳定、和库里那行一一对应，这是它存在的意义。

键要稳定。

避坑提醒：列表"玄学问题"，七成出在键上

勾选状态莫名串行、删除后动画乱跳、偶发两次 onChange，遇到这类说不清道不明的列表问题，先别怀疑人生，回头检查键生成器。把它换成唯一的 id，这类玄学问题大半当场消失。这一条值回本章票价。

空状态：新用户的第一眼不能是一屏空白

刚装好的应用，数据库是空的，列表也是空的：用户看到的就是一块白板，不知道该干嘛。空状态就是给这个时刻准备的：一张简单的插图或一个图标，一句"还没有待办"，一个"添加第一条"的按钮。实现不难，在 build 里用 if/else 分支判断数据源长度：

if (this.todos.length === 0) {
  Column() {
    Text('☑').fontSize(48).opacity(0.4)
    Text('还没有待办，添加第一条吧').margin({ top: 8 })
    Button('添加待办').margin({ top: 16 })
      .onClick(() => { this.showInput() })
  }
  .justifyContent(FlexAlign.Center)
  .layoutWeight(1)
  .width('100%')
} else {
  List({ space: 8 }) { /* 前面的列表 */ }.layoutWeight(1)
}

注意 layoutWeight(1) 让空状态垂直居中，而不是顶在屏幕上方孤零零一行。空状态文案别写成"数据为空（0 条）"这种机器话，用户不是程序员，说人话。将来做分类、做筛选之后，空状态要跟着细分成"这个分类还没有待办"和"今天的事都做完啦"两种，后者是好消息，别用报错的语气说它。

勾选交互：先改库，再刷新

Checkbox 上有两个方向的数据流：.select(t.done) 是"往里写"：用数据回显当前状态；.onChange 是"往外读"，用户点了勾，把新状态交给你。顺序千万别搞反：onChange 里先调用 db.toggle 把库改掉，等它完成后再回查刷新 @State，让界面从库里"长"出来。不要图省事在 onChange 里手动改数组里的对象：那样界面和库就可能短暂不一致，一旦刷新逻辑出了岔子，你会看到"勾明明打了、杀掉重开又变回去"的灵异现场。

删除线是纯属性调用：.decoration({ type: ... })，完成的加 LineThrough，没完成就 None。顺手再补一点视觉弱化：完成的行整体调低透明度（.opacity(t.done ? 0.5 : 1)），一眼扫过去，没做的和做完了的分层清楚。这种小改动一行代码，但"扫一眼知道还剩几件事"正是待办清单的核心体验，值得做。

还有一个交互细节：勾选时 Checkbox 自带的选中动画已经有了，但文字的删除线是"啪"一下出现的，生硬。给 Text 挂上 .animation({ duration: 200, curve: Curve.EaseInOut })，透明度和删除线的变化会变成一段小过渡。动画参数没有标准答案，两百毫秒左右、缓入缓出，是多数场景不会出错的一档；具体支持的参数形态以官方文档为准。

滑动删除：把"删除"从行里挪出来

骨架代码里"删除"是行内一个红字按钮，能用，但占地方，还容易误触。移动端的惯例是滑动删除：把行往左一划，露出一个删除按钮。ArkUI 的 ListItem 自带这个能力，swipeAction 一个属性的事：

ARKTS · 给 ListItem 加滑动删除···
ListItem() {
  // ……行内容：Checkbox + Text……
}
.swipeAction({
  end: {
    builder: () => {
      Text('删除')
        .fontColor(Color.White)
        .backgroundColor(Color.Red)
        .borderRadius(8)
        .padding({ left: 14, right: 14 })
        .onClick(() => {
          this.db.remove(t.id).then(async () => {
            this.todos = await this.db.list()
          })
        })
    }
  }
})

swipeAction 的 end 表示从右侧划出（start 则从左侧），builder 就是划出来露出的那块界面；参数的完整形态以官方文档为准。做了滑动删除，行内的红字"删除"就可以撤掉，行面干干净净——这正是交互设计里"低频操作藏起来，高频操作露出来"的具体落地。删除是危险操作，所以下一节会讲要不要加二次确认，以及比确认框更优雅的"撤销"方案。

从预览器到真机：第一次完整跑起来

代码写完，别一头扎进真机。跑起来这件事分三级台阶，一级比一级接近真实环境；逐级往上走，出了问题你才知道该在哪一级找原因。

  1. 预览器看布局：IDE 的预览器对界面改动即时刷新，调样式、对齐、间距都在这里最方便，但它对系统能力（数据库、生命周期这些）的支持有限，别在这里下"功能能不能用"的结论。
  2. 模拟器跑全功能：模拟器里数据库、弹窗、软键盘都能真跑，第一轮功能验证全放在这一级。
  3. 真机准备：手机设置里打开开发者模式，连上电脑并允许 USB 调试（入口位置随系统版本不同，按官方指引找）。
  4. 命令行敲 hdc list targets，确认设备真的连上了：没连上先解决连接，别怀疑代码。
  5. IDE 点运行（或 hdc install 装包），第一次会遇到签名问题，按官方指引开通自动签名即可，之后不再烦你。
  6. 应用拉起后，连续添加三条不同标题的待办，挨个试勾选、滑动删除。
  7. 杀掉进程重新打开，数据还在，持久化的第一课就算结业了。
  8. 最后卸载重装一次，数据清空。这步看着多余，其实是在给你现场演示"卸载即清库"，第八节病号六讲的就是它。

这一轮走完，"我的应用在我的手机上活着"就有了第一手证据。以后每次改完代码，重跑第六、七两步验证主流程，三十秒的事，能挡住大部分低级回归。

错误示范：某人的列表页翻车记

给你看一个反面样本。有人跟着敲完骨架，跑通了，很开心，开始"自由发挥"，然后一周之内翻了三次车。三次翻车都有完整现场，逐个看。

翻车现场

键生成器嫌麻烦，直接写成 t.title。理由听着很充分：id 还要 toString，标题现成的。第二天他添加了两条"买牛奶"（测防重复时把查重逻辑注释了），从此勾选开始串行：勾了第一条，第二条跟着划线。

"勾了第一条，第二条也跟着划线了"

场景来源：全书通用场景（非特定读者）

怎么办：框架靠键认行，两条同键数据在它眼里就是同一个人。改回 id，当场恢复。键生成器是列表更新的命脉，不是可以省的那一步。

错误二：嫌回查啰嗦，在 onChange 里直接改数组元素。他把回调写成了给某一项的 done 赋值。屏幕上看一切正常，杀掉重开，勾选状态全回去了——库压根没改，他改的只是内存里的临时副本，而界面恰好配合演出。单一数据源原则不是美学洁癖，是防这种"精神分裂"的。修复：回到先改库、再回查的标准流程，一行都不能省。

错误三：不知道初始化该放哪，把 db.init 写进了 build()。结果 build 每次重绘都执行一遍 init，控制台错误刷屏，应用越用越卡。build 是渲染函数，框架想调就调，任何"只该干一次"的事都不能放这里——初始化归 aboutToAppear，这是第 74 章定好的分工。

三次翻车，三次都能在正文里找到对应的划线句。这不是巧合：教程能替你踩的坑有限，剩下的坑就是留着翻的：翻完回来翻书，记忆反而最牢。

给行加一点"人味"：七个小细节

骨架是功能性的，离"好用"还差一层皮肤。下面七个细节按性价比排了序，做满三个，界面立刻不一样：

做满三个。

  • 完成的行文字降一档透明度，扫一眼就能分清"没做的"和"做掉的"。
  • 未完成条目左侧加一条细色条，用主题色，勾选完成即消失：比图标省事，比背景色克制。
  • 标题下面配一行小字辅助信息：创建时间，或者做完练习一之后的截止时间。
  • 长标题 maxLines 加省略号，点行展开看全文，两行是列表行的甜点位，再多就成详情页了。
  • 删除按钮和滑出区域给足触摸热区，别让长辈对着一粒小红字练指法。
  • 分割线用极浅的颜色，或者干脆靠间距分行，过重的分割线会让列表看起来像表格。
  • 整行可点（点行展开详情），但要让 Checkbox 自己吃掉自己的点击事件，不然点一下勾会连着触发行点击。

这些细节没有一个是"必须"的，而这正是它们的价值：做完它们，你的应用开始像一个被人惦记过的产品，而不只是一个跑起来的教程。

三、输入与添加：弹窗、校验、防重复

骨架里的输入框是顶部一行 TextInput，能跑，但有几个现实问题：标题长的时候两块挤在一行谁都不舒服；地铁上单手操作，够最顶上的输入框很费劲；输入框常驻还占掉了列表的地盘。所以这一节把它升级成弹窗输入：点一个"＋"按钮，弹出输入面板，填完确认，面板收起。这也是你在各类待办应用里最常见的形态。

弹窗输入：一个自定义对话框

ArkUI 里做输入弹窗有好几条路：AlertDialog 放自定义内容、CustomDialog、半模态 bindSheet。这里用 CustomDialog 演示，它的结构最清楚：一个独立的小组件，自带开关控制：

ARKTS · view/TodoInputDialog.ets···
@CustomDialog
struct TodoInputDialog {
  controller?: CustomDialogController
  onConfirm: (title: string) => void = () => {}
  @State text: string = ''

  build() {
    Column() {
      Text('添加待办').fontSize(18).fontWeight(FontWeight.Bold)
      TextInput({ placeholder: '要做什么？' })
        .margin({ top: 12 })
        .onChange((v: string) => { this.text = v })
        .onSubmit(() => { this.confirm() })
      Row({ space: 12 }) {
        Button('取消')
          .backgroundColor(Color.Gray)
          .onClick(() => { this.controller?.close() })
        Button('添加')
          .onClick(() => { this.confirm() })
      }
      .margin({ top: 16 })
      .justifyContent(FlexAlign.End)
      .width('100%')
    }
    .padding(16)
  }

  confirm() {
    this.onConfirm(this.text)
    this.controller?.close()
  }
}

对话框只干一件事：收文字，然后把文字通过 onConfirm 回调交出去：注意它不碰数据库、不碰列表，校验和入库都在页面侧做。这样这个对话框以后在"编辑"场景里还能复用（第五节会用到），这就是第 37 章说的"封装变化点"。页面里挂上控制器：

ARKTS · 在页面里接上对话框···
dialogController: CustomDialogController = new CustomDialogController({
  builder: TodoInputDialog({
    onConfirm: (title: string) => { this.addTodo(title) }
  })
})

showInput() {
  this.dialogController.open()
}

把原来顶部的输入行换成一行工具栏：左边标题"今日待办"，右边一个"＋"按钮调 showInput()。列表瞬间多出一整行的呼吸空间。键盘弹起时的遮挡避让，系统有默认行为，一般不用管；如果你的弹窗被键盘压住了输入框，去查键盘避让相关的配置项，以官方文档为准。

校验：把脏数据挡在门口

用户不会按你以为的方式输入。有人一个空格回车连按五下提交一条"看不见的待办"；把一整篇笔记粘贴进来，列表行会被撑成一大团；输入到一半手滑点了取消。校验要做的就是把这几类脏数据挡在 addTodo 门口：

ARKTS · 带校验的 addTodo···
async addTodo(raw: string) {
  const title: string = raw.trim()
  if (title === '') {
    this.toast('先写点内容再添加吧')
    return
  }
  if (title.length > 50) {          // 阈值是示例，自己定
    this.toast('标题太长了，拆成几条更清爽')
    return
  }
  await this.db.add(title)
  this.todos = await this.db.list()
}

三步校验，每一步都对应一类真实翻车。trim() 吃掉首尾空白，纯空格的输入在这里现出原形；长度上限防的是"粘贴党"，50 只是示例阈值，你按自己的产品感觉定；两处都给出友好的提示文案而不是沉默失败——用户不知道为什么按钮"没反应"比功能缺失更劝退。

防重复：同名待办要不要拦？

防重复是个产品判断题，不是技术题。技术上一行的事：入库前查一下 this.todos.some((t: Todo) => t.title === title)，命中就提示"已经有一条一模一样的了"。但要不要拦，想一个场景：周报每周都要写、垃圾每周都要倒，同名待办在清单应用里是合理需求，硬拦反而惹人烦。

给你一个折中方案：查重时只对"还没完成"的同名条目提示，并且提示里给两条路："仍然添加"和"算了"。也可以更轻：不拦。但新加的同名条目后面自动跟上序号或时间，让用户自己能分清。判断标准就一条：重复是用户故意为之还是手滑，手滑要拦，故意的要配合。数据层的 add 不用改：查重在页面侧用已有数据做就够了，别为这个专门发一条 SQL，列表里现成有。

回车提交与软键盘：输入的最后一公里

TextInput 的 onSubmit 已经把回车接成了提交，但软键盘还有几个可调的细节值得顺手做掉：右下角那个键的文字（完成、发送这一类）可以按场景配置，输入待办配"完成"最顺；弹窗打开时让输入框自动聚焦，键盘直接弹起，用户少点一次（自动聚焦与键盘控制的具体接口以官方文档为准）。提交成功后把弹窗里的文字清空、键盘收好，别让用户收面板时又看到"买牛奶"还躺在框里，产生"到底加没加上"的疑惑。

还有一个反直觉的原则：输入过程中不要用校验打断用户。长度超限在提交时拦就够；真想做实时提示（比如字数快到上限），让提示安静地待在输入框下方一行小字，别弹窗、别抖动、别标红闪烁。校验的存在感越低，用户越愿意把内容输完：这一条和"防重复要拦"并不矛盾：打断输入的是噪音，拦住提交的是门槛，前者越少越好，后者要看得清。

添加后的即时反馈：让新条目"报到"

默认排序下新条目排在最顶上（list() 用的是 ORDER BY id DESC），本来就该一眼看到。但等你做完练习一或练习二，列表改成按截止时间或分类排序，新条目可能落在屏幕外，"我明明添加成功了，它去哪了"会变成高频困惑。两个补救思路：添加成功后把列表滚回新条目所在的位置（滚动定位接口以官方文档为准）；或者更简单，给刚加入的条目一个短暂的高亮背景。

高亮的实现思路：用一个 @State 记住"最近添加的条目 id"，行的背景色按它判断，几百毫秒后用定时器清掉。注意两件事：定时器用完要清理，组件销毁前也要清，第八节和 FAQ 里念过的清理纪律，这里是现场应用；另外高亮只用背景色的轻量变化就够，别上弹跳缩放，"报到"不等于"蹦迪"。

一条待办的完整旅程：把链路串一遍

功能都通了之后，做一件很有用的事：在心里跟着一条待办走完全程。拿"周四给爸妈打电话"当样本：你在弹窗里敲字，onChange 把每个字符交给弹窗自己的状态；点添加，回调把文字交给页面的 addTodo；trim 校验、查重两道门过掉；db.add 执行 INSERT，数据落盘；回查 list()，@State 整体替换；键生成器为新行报出新键，ForEach 渲染，transition 让它渐入。十几个环节，一气呵成，全程不到一秒。

这条旅程的价值在排错：任何一环断了，症状都不一样。断在校验，按钮像没反应；要是断在 INSERT，杀掉重开数据没了；断在回查，库里有货列表不动；最后是键断了，行渲染串位。第八节的门诊是对照表，这一段是电路图——照着数据流找断点，比背症状快得多。以后你给这条旅程加站（练习一到五每道题都是在链路上加站），每一站加在哪、断了会怎样，你都能自己推演出来。

避坑提醒：输入框的两个"灵异现象"

现象一：光标莫名跳动、文字忽长忽短——多半是 onChange 里回写 @State 再绑回 text 属性引发的重绘冲突，遇到时试着让输入框自己持有文字，提交时再取值。现象二：弹窗弹出后输入框拉不起键盘——检查弹窗是不是在页面还没完全就绪时就打开了，把 open() 挪到点击事件里而不是生命周期回调里。这两类现象随版本表现不一，以实机为准。

四、完成与删除：状态切换动画与批量操作

单条勾选和单条删除前面都能跑了，这一节处理"上量"之后的体验：条目进出列表时的动画，以及删掉十条已完成的待办不应该点十次按钮。先说动画，因为它和键生成器咬合最紧。

条目进出的过渡动画

新增一条待办，理想效果是新行从上滑入；删一条，剩下的行平滑补位。这套效果靠 transition 属性实现——它定义的是"条目出现和消失时怎么动"，配合 ForEach 的增删自动触发：

ARKTS · 给 ListItem 挂过渡···
ListItem() {
  // ……行内容……
}
.transition(TransitionEffect.OPACITY.animation({ duration: 250 }))

这里是透明度渐入渐出，你也可以组合位移、缩放做出更讲究的效果，具体能组合哪些效果以官方文档为准。关键前提只有一个：键生成器必须稳定。键是框架识别"谁出现了、谁消失了"的唯一依据，键一乱，transition 要么不触发要么乱触发，又一次，列表问题绕回键上。做动画时把这条记牢，能省下大量"为什么动画时灵时不灵"的debug时间。

删除要不要二次确认？

删一条待办，要不要弹"确定要删除吗"？很多教程默认要。但交互设计里有个更细的判断：操作越难撤销，越需要确认；操作容易撤销，确认反而是打扰。待办清单里单条删除的代价很低（大不了重新加一条），所以业界常见做法是不弹确认，改成"删除后短暂提示可撤销"，删完立刻弹一个带"撤销"按钮的提示，几秒后自动消失。这条路的实现思路放在第九节的练习里，比确认框的体验顺滑得多。

作者立场

我的结论：单条删除不弹确认框，改成"撤销提示"；批量删除和"清空已完成"必须弹确认。理由三条：

  • 待办清单里单条删除的代价很低——大不了重新加一条，确认框在这里是纯打扰；
  • "删除后弹一个带'撤销'按钮的提示，几秒后自动消失"，既保住了可逆，又不打断操作节奏；
  • 一次动作影响很多条（批量删除、清空已完成）时，误操作没法靠"再加回来"补救，确认必须留着。

（无利益相关。对话框与提示组件的具体写法以官方文档为准；不同平台系统规范对确认提示的要求可能不同，以你所用平台的规范为准。）

但"清空已完成"和"批量删除"不一样：一次动作影响很多条，必须确认。对话框可以复用系统的 AlertDialog（建议通过 UIContext 调用，写法上和前面拿 Context 的思路一致，参数形态以官方文档为准）：

批量操作先从数据层加方法开始，SQL 一句的事：

界面侧两种形态。轻量版：工具栏放一个"清掉已完成"的文字按钮，点了走上面的确认流程，覆盖八成需求，成本最低。完整版：长按进入多选模式，每行左边 Checkbox 变成选择框，底部浮出工具条显示"已选 N 条"，带全选和删除按钮。完整版的状态管理稍复杂，加一个 @State selecting: boolean 和一个记录已选 id 的容器，退出多选模式记得清空，做一遍很练状态设计，建议先上轻量版把流程跑稳，再做完整版。

顺手补一个容易忘的细节：批量删除后的空状态。用户把清单清光之后，界面应该给一句"都清完啦"，而不是又落回"还没有待办，添加第一条吧"——同一个空态，两种语境，文案多写一行，体验差出一个档次。

小贴士：动画和确认框，都先问"用户此刻在想什么"

加任何效果前先代入用户：勾选完成时他心里是"干掉一件事"的爽感，动画就顺着这个方向做：删除线扫过、行下沉变灰；删除出错时他心里是"完了删错了"，这时候要给的不是动画，是一条退路。效果不是越多越好，是对得上情绪才好。

五、编辑与详情：长按编辑与优先级标记

到这里，这个应用只会"加"不会"改"——手滑打了错别字，只能删了重加。编辑功能是增删改查闭环里最后一块，也是你之前那个"来动手"练习的目标，这里完整走一遍，顺带把详情和优先级一起做了。

长按进入编辑

移动端惯例：点按行是"查看/详情"，长按行是"编辑/更多操作"。长按用手势能力实现，挂给行组件：

无障碍提醒在这里插一句：长按对读屏用户是"隐形"操作：摸不到就等于不存在。给行补一个可见的替代入口，比如行尾一个"更多"图标。点开菜单里有编辑和删除；或者读屏开启时长按手势的描述要能被播报出来（accessibilityText 一类的属性，用法以官方文档为准）。这一条看似边缘，做与不做，长辈用户和视障用户的体验是两个世界。

优先级：模型演进与表结构迁移

想给待办标"重要/普通"，模型就要动——这正好是一次完整的"模型演进"实战。动模型要连改三处：Todo 接口加字段、建表 SQL 加列、读写方法带上新字段。前两处好改，麻烦在第三处之外：已经装了旧版应用的设备上，表还是旧结构，CREATE TABLE IF NOT EXISTS 对已存在的表什么都不会做，新代码查询新列，直接报"no such column"。

这就是版本迁移问题，标准解法是"给数据库记版本号，启动时补差异"。SQLite 的 ALTER TABLE ADD COLUMN 正好支持给已有表补列：

ARKTS · init 里补列（迁移思路）···
async init(context: Context) {
  this.rdb = await relationalStore.getRdbStore(context, {
    name: 'todo.db',
    securityLevel: relationalStore.SecurityLevel.S1
  })
  await this.rdb.executeSql(
    'CREATE TABLE IF NOT EXISTS todo ' +
    '(id INTEGER PRIMARY KEY AUTOINCREMENT, title TEXT NOT NULL, ' +
    'done INTEGER DEFAULT 0)')
  // 迁移：给老库补 priority 列。生产做法是先查表结构确认缺列再补，
  // 简化版直接试着加，列已存在会报错，捕获后忽略即可
  try {
    await this.rdb.executeSql(
      'ALTER TABLE todo ADD COLUMN priority INTEGER DEFAULT 0')
  } catch (e) {
    // 列已经存在，说明是新版库，跳过
  }
}

这个"试着加、报错就跳过"的写法适合练手项目；讲究一点的做法是把表结构版本号存进一张 meta 表（或 Preferences），启动时比对版本决定执行哪段迁移，将来加第二个第三个字段时才不会堆成一团 if。现在你可以只记住原则：改表结构的代码必须对"老库"和"新库"都成立——练手时简单，上架后就是真用户的真实数据，删库跑路的喜剧都是在这儿上演的。

界面呈现优先级用最朴素的方式。priority 为 1 的条目，标题前面加一个红色小圆点，或者行左边加一条竖色条。别一上来就做四种颜色五个等级：等级越多用户越不知道选哪个，两档（重要/普通）是清单应用的甜点位。详情也一样：点按行展开行内详情（创建时间、优先级），比单独跳一个详情页轻得多，够用；以后真要做完整详情页，页面跳转用 Navigation 一类的官方方案，本章不展开。

来动手：把编辑做成完整闭环

照本节路线动手：长按行弹出复用的输入对话框，预填原标题，确认后走 update 落库、回查刷新。做完顺手用命令行过一遍流程：hdc list targets 看设备、hdc install 装包、hdc shell aa start 拉起应用：命令行比在 IDE 里来回点快得多。最后故意改模型再跑一次老库（先装旧版造数据，再装新版），亲眼看看"no such column"长什么样，你对迁移的理解才算长在身上。

六、数据统计：完成率与历史趋势的小组件

清单用起来之后，人会开始好奇"我今天完成了多少""这周勤不勤快"，这是给应用加数据统计组件的时机，也是练"聚合查询"的好场景。先做一个顶部完成率卡片，再做一个小小的历史趋势。

完成率卡片：COUNT 聚合，不是拉全表来数

完成率的算法看着简单：完成数除以总数。但实现路径有讲究，坏路径是把 list() 的全部数据拉回来在界面层过滤计数；好路径是让 SQL 聚合，一行数据都不用搬运：

ARKTS · TodoModel.ets 加统计···
export interface TodoStat {
  total: number
  done: number
}

async stat(): Promise<TodoStat> {
  let out: TodoStat = { total: 0, done: 0 }
  let rs = await this.rdb?.querySql(
    'SELECT COUNT(*) AS total, SUM(done) AS done FROM todo')
  if (rs?.goToNextRow()) {
    out.total = rs.getLong(rs.getColumnIndex('total'))
    let d = rs.getLong(rs.getColumnIndex('done'))
    out.done = d === null ? 0 : d   // 空表时 SUM 返回空值
  }
  rs?.close()
  return out
}

两处细节值得圈出来。一是 SUM(done) 对空表返回的是空值而不是 0，直接 getLong 可能出问题，判一下空，这是新手统计代码最常见的崩溃点。二是 rs 用完记得 close，结果集不关，资源就悬着。界面侧配一个环形进度：

ARKTS · 完成率卡片···
Row({ space: 12 }) {
  Progress({ value: this.stat.done, total: this.stat.total || 1,
             type: ProgressType.Ring })
    .width(44).height(44)
  Column() {
    Text(`${this.stat.done}/${this.stat.total} 已完成`)
      .fontSize(16)
    Text(this.stat.total > 0 && this.stat.done === this.stat.total
         ? '今天全清完啦' : '再接再厉')

  }

}
.width('100%')
.padding(12)

.margin(12)

total 为 0 时给分母兜个底，避免除零类的显示异常；全部完成时把"再接再厉"换成"今天全清完啦"，统计数字是冷的，文案让它暖一下。这张卡片放在列表上方，@State 里加一个 stat 字段，每次增删改之后和列表一起刷新即可。

历史趋势：先把 createdAt 补进模型

做趋势的前提是数据里有时间。还记得第一节说过"以后想按时间排序就得有 createdAt"吗？现在到了兑现的时候：模型加 createdAt 字段，建表 SQL 加列，add 方法里把 Date.now() 存进去——迁移的写法照第五节 ALTER TABLE 的套路来，不再重复。存毫秒时间戳是最省事的方案，排序、比较、按天分组都方便。

趋势的最小可用版：最近七天，每天新增多少条、完成多少条。SQL 按天分组当然可以做到（SQLite 的日期函数能干这活，写法以官方文档为准），但练手阶段有个更直白的路子：界面侧循环七天，每天用一条带时间范围的 COUNT 查询。七次查询听着不优雅，但逻辑一目了然，而且你的个人清单一天能有几条数据？性能根本不构成问题。等数据量真上去了，再换成一条 GROUP BY 的聚合 SQL——先跑通，再优化，这个顺序别反。

趋势的呈现不用上图表库：一行七个竖条，条高按数量缩放，底下标"一二三四五六日"，三十行代码以内搞定。数据统计组件有个共同的设计纪律：只展示"能改变行为"的数字。完成率让人想清零，连续完成天数让人不想断，这些有意义；至于"平均每个待办 11.5 个字"这种能算出来但没人需要的指标，忍住别做，做了只会让卡片变挤。

七、优化与打磨：字体、间距、深色模式、无障碍

功能闭环之后，接下来这一节的活儿决定它是"课程作业"还是"能日常用的应用"。四件事：字体、间距、深色模式、无障碍。都不难，但每一件都需要你主动去测，不是写完代码自动就有。

字体：字号用 fp，跟着系统走

系统设置里调大字号，多少应用当场排版崩掉，原因就是开发者把字号写死了。ArkUI 里字号单位有 vp 和 fp 两个：vp 是布局单位，fp 是字号单位、会跟随系统字号缩放。给 Text 指定 fontSize 时用数字或 fp，别用写死像素的思路；标题、正文、辅助说明拉开层级（比如 18、16、13 一档），别全文一个号。长标题记得 .maxLines(1) 加省略号，防止一行撑爆卡片。

测法很笨但有效：系统设置把字号调到最大档，回到应用从头滚到尾，哪行字溢出、哪行换行难看、哪个按钮被顶飞，记一条改一条。再切回正常字号确认没改坏。长辈用户十个里八个开着大字号，这一步不是可选项。

间距：一套栅格，全页统一

排版"说不上来哪里不对"的时候，多半是间距不统一：这里 padding 10、那里 padding 12、卡片之间一处 8 一处 16。定一套自己的栅格：间距只用 4 的倍数（4、8、12、16、24），页面级边距统一一个值，卡片内边距统一一个值，行内间距统一一个值，然后全局照此执行。更规范的做法是把这几个值抽成常量或资源引用，改一处全局生效。半天的功夫，观感的提升立竿见影。

深色模式：别把颜色写死

白天用的应用，晚上刺眼——用户切了深色模式，你的应用如果背景写死了白色，就成了屏幕里最亮的那块补光灯。ArkUI 的正规做法是把颜色定义成资源：普通色值放在默认资源目录，深色专用的值放在对应的深色资源目录里，同名资源系统自动切换：

ARKTS · 资源色（示意）···
// 页面里不写 Color.White，引用资源色：
.backgroundColor($r('app.color.page_bg'))

// 默认目录的 color.json：
// { "name": "page_bg", "value": "#FFFFFF" }
// 深色目录的 color.json：
// { "name": "page_bg", "value": "#1C1C1E" }

// 系统切深色，同名资源自动换成深色值，代码一行不用改

资源目录的具体路径和文件格式以官方文档为准，思路就一句话：颜色是资源，不是代码。文字颜色同理，别在浅色背景上写死黑色文字然后指望深色背景上它自动变白，它不会。做完在系统设置里切一次深色模式，把每一页截图对比：背景、文字、分割线、按钮、删除线的红色在深色下都不能刺眼。红色删除按钮在深色背景上常常要换成亮度低一档的红，纯 Color.Red 深色下看着像报警器。

无障碍：让读屏用户也能用

读屏（视障用户靠语音播报操作手机）开启路径在系统的辅助功能设置里，具体名称视机型与系统版本而定。开一遍读屏，戴上耳机，闭着眼把这个应用完整用一遍：能不能听到每行待办的内容？勾选 Checkbox 时有没有播报"已完成"？长按编辑的手势读屏用户怎么触发？凡是"只靠看"的交互（红色代表删除、删除线代表完成），都要补上语义描述，给 Checkbox 挂上类似"把某某标记为已完成"的描述属性，用法以官方文档为准。

前面两节埋的两处伏笔在这里收口：滑动删除对读屏用户同样不可见，所以要留行内可见的删除入口或"更多"菜单；长按编辑要给可见的替代路径。还有对比度——灰色文字在浅灰背景上是"看起来高级"，对低视力用户是"看不见"。这些改动每条都是小活，加起来就是"能不能被更多人用"的分界线。

启动速度：让第一屏快起来

应用的口碑有一半在冷启动那几秒里。这个项目的页面本来就很轻，aboutToAppear 里只有一次 init 加一次查询，没有网络、没有重计算，这是好消息；但"轻"是设计出来的，不是碰巧的。守住三条：生命周期回调里不做重活（数据读写之外的计算、格式化别塞进 aboutToAppear）；统计这类数字走第六节的聚合查询，别为了算个数把全表拉进内存；列表真变大了，再考虑换 LazyForEach。FAQ 里说过判断标准，实测卡了才换。

还有一个体验细节值得做：加载状态。真机首次启动时 init 和查询需要一点时间，这段时间界面是白板还是骨架，观感差很多。加一个 @State loading: boolean，初始为 true，init 和首查完成置 false；界面上 loading 为 true 时显示一个加载指示加一句"正在打开你的清单"，数据到位再切换到列表。几行代码，把"卡了？"和"正在加载"两种完全不同的用户心理分开了：前者是差评，后者是等待。

打磨收尾，把那条最便宜也最值钱的保险补上：三条单元测试，「新增一条，列表长度加一」「勾选一条，状态翻转」「全删掉，列表归零」。DevEco 自带测试框架，这类纯逻辑的断言写起来很快（接口方法以官方文档为准）。现在它们只是三个绿勾；等你哪天升级 SDK、重构数据层的时候，它们就是告诉你"没改坏"的三张保票。

小贴士：发给自己用之前的五分钟自查

字号调到最大滚一遍；切深色模式截两张图对比；开读屏闭眼走一遍主流程；飞一次飞行模式确认本地功能照常（这应用本来就该离线能用）；杀掉应用重开，确认数据还在。五分钟，五项全过，你就可以把它当真应用用了。

别让打磨清单吓退你：分三批做

这一节的清单全堆在面前，容易直接摆烂——它本来就该拆开吃。第一批，当场做：maxLines 省略、完成行透明度、空状态文案，全是一两行的改动。第二批，凑一个周末：深色资源色迁移、间距栅格统一、加载状态，这几件要动资源目录、要全局替换，适合整块时间。第三批，想在主屏长住之前做：读屏自查、对比度、三条单元测试，它们要么要学新工具，要么要新习惯，放最后。分批的判据就一条。一行的改动当场做，要新建目录新资源的攒着做，要学新工具的最后做。

每批做完都跑一遍主流程验证，别攒三批一起验，验证间隔越长，出了问题越难定位是哪批引入的，第八节的排错心法在打磨期同样管用。

打磨的两个反模式

反模式一，打磨变重构：本来只想给标题加个省略号，顺手把数据层重构了，两小时后应用跑不起来。打磨和重构是两种工装，混用必翻车。打磨期间唯一允许的代码行为是改样式、改文案、改资源；想动结构，单开一天，开新分支，跑完测试再合。

反模式二，磨皮不填坑：入场动画调了两小时，大字号自查一次没跑过。排打磨优先级的标尺是"用户每天会碰到几次"，字号和深色是天天碰的，入场动画是一辈子看一次的，顺序不言自明。每次想给界面加效果之前，先看一眼第一批清单做完没有，那是所有效果的地基。

界面之外：名字与图标

还有两样天天见的东西，最容易被新手应付过去：应用名和图标。名字别叫 MyApplication，更别叫"测试1"：给它一个真名字，比如"今日清单"，你自己点开它的意愿都会翻倍。图标用最简单的方案：主题色底、一个对勾或圆点，不追求精致，追求一眼认得出。具体怎么配图标资源，按官方文档的向导走即可。

名字和图标的深层价值在心理：当你把一个项目当成"有名字的东西"来对待，你会自然开始在意它的体验、愿意给它做备份、舍不得随手删掉它的数据。项目长成产品的第一步，往往就是命名，这一步不花十分钟，但值得认真花。

打磨也做减法

打磨不全是加东西。写完加法清单，回头审一轮减法：用不上的按钮撤了吗？只有一种状态下才有用的选项，藏进"更多"了吗？提示文案里客套的"请"和"您"删掉了吗？首页那一行谁都不会读的说明文字，留着干嘛？每一次做加法之前先做一轮减法，界面轻一分，重点才亮一分。这一章给你的都是加法清单，减法永远靠你自己审，因为只有你知道哪些东西是你永远不会点的。

八、常见 bug 门诊：八个高频症状的诊断路径

这一节按"症状 → 大概率原因 → 修复"的门诊格式写。写项目时对照自查，跑不通时按图索骥，这八个病号覆盖了这个项目大部分的新手求助帖。

病号一：添加成功了，列表不动。最常见的原因是改了库没刷新状态，或刷新姿势不对——有人写成 this.todos.push(x)，以为数组内容变了界面就该动，但 @State 对这类原地修改的感知不可靠，界面经常不给面子。修复姿势统一为整体赋值：this.todos = await this.db.list()，整组替换，界面必然重画。排查顺序：先确认库操作 await 了没有，再确认回查写了没有，最后检查键生成器有没有让框架误判"数据没变"。

病号二：删除错位，删 A 行 B 行没了。典型的键生成器事故：键用了 index 或会重复的 title，框架把"删掉一条"理解成"中间几条换了内容"，重建出来的行和你的闭包对不上号，点了删除按钮删的是别的行。修复只有一条路：键用数据库主键 id，第二节的避坑提醒就是为它写的。另一个同名症状是滑动删除的回调里捕获错了 t——每个 builder 闭包要绑定它自己那一行的数据，写法以官方文档为准。

病号三：报 rdb 为空、no such table，时好时坏。大概率是异步时序问题：aboutToAppear 里 init 是异步的，init 还没完成，界面或别的代码已经开始调 list()——rdb 还是 null，可选链 ?. 把错误静悄悄吞掉，表现就成了"有时好有时坏"。修复：所有库操作都排队等 init 完成再发车（Promise 串行），把 ?. 静默失败换成失败时明确报错。另一个同症状的原因是 new 了两个 TodoDb 各自 init 了一份数据库——数据层做单例，全应用共用一个实例。

病号四：连续快速点"添加"，偶发数据库报错。典型的并发写入问题：上一个写操作还没落盘，下一个写又压上来，同一连接上的写请求打架（报错文案各版本不一，大意是数据库忙或锁住）。修复三选一：写操作加一个简单的串行队列；把"连点"在界面层防掉（提交后按钮短暂禁用）；或者干脆接受偶发失败、失败时提示重试。个人清单应用里第一种最省心——十几行代码，所有写操作排一列纵队。

病号五：编译告警 getContext is deprecated。全局 getContext 从 API 18 起废弃，官方方向是全部走 UIContext。修复：this.getUIContext().getHostContext()。顺带记住这个模式：弹窗、吐司这类"必须知道界面在哪儿"的全局接口，新版本同样建议通过 UIContext 调用——你在 UI 组件里就 this.getUIContext()，别的地方把 UIContext 传过去。以后再遇到 deprecated 告警别慌，读一眼告警信息里的替代写法，基本都指着这条路。

病号六：真机上数据"丢了"。先别怀疑代码。最常见的三种"丢法"：卸载重装（应用数据连库一起清）；换了设备测（模拟器、真机、预览器各自的存储互不相通，数据各存各的）；安装方式不对（某些情况下先卸载再装等于清库）。诊断动作：杀掉应用不卸载重开一次——数据还在，说明存储没问题，是"清库动作"发生在装包环节。预防：升级版本用覆盖安装，别手痒先卸载；重要数据做导出备份（第九节练习四就是给它准备的）。

病号七：键盘收起后，界面底部空出一条键盘高度的空白。多半是手动干预过窗口避让——为了防止键盘挡输入框，代码里自己设过窗口高度或避让模式，键盘收起后设置没跟着还原。修复方向：先把手动避让撤掉，用系统默认的避让行为跑一遍；确有特殊需要再按官方文档的键盘避让配置来，别手写高度。预防：凡是"系统有默认行为"的地方，先信默认，实测不够再定制——这条和第五节"先用免费额度"是同一个思想。

病号八：切了深色模式，列表一半白一半黑，特别刺眼。一半白说明有一部分颜色写死了——某个卡片背景写了 Color.White，或某行文字写死了深灰色，它们不跟系统走；另一半黑的走了资源色。修复：全局搜一遍 Color. 开头的直接引用，逐个换成资源色，深色目录里补上对应值——第七节深色模式那一小节就是完整修法。预防立个规矩：新组件从第一天就引用资源色，写死一个颜色，等于给未来的自己埋一颗刺眼的雷。

门诊看完总结一条规律：这八个病号里，三个出在键生成器或刷新姿势上，两个出在异步时序上，剩下的是环境与配置问题。技术含量最高的修法前面全讲过了：整体赋值刷新、键用 id、init 排队、单例、资源色。把这几条变成肌肉记忆，你的待办应用就很难再进这家门诊；就算来了，你也知道挂号处在哪。

九、功能扩展练习：五个进阶题，自己搭梯子

跟着做完一整章，容易产生"我都会了"的错觉：检验的真办法只有一个：脱掉教程自己加功能。下面五道题按建议顺序排，每道都给目标和提示，不给答案。做完两道以上，你就从"照着敲的人"变成"能自己写的人"了。

练习主要练什么建议顺序
截止时间与排序模型迁移、排序查询1（衔接第五节最顺）
分类与筛选查询条件、状态联动2
撤销删除交互设计、时序控制3
导出与备份文件读写、JSON4
桌面卡片跨组件数据呈现5（进阶收尾）

练习一：截止时间与排序。目标：每条待办可以设一个截止时间，过期的标红，列表按"紧急程度"排序而不是默认的新增顺序。提示：模型加 dueAt 字段（迁移照第五节 ALTER 的套路）；list() 加一个排序参数，SQL 的 ORDER BY 按需排；界面给过期条目换色、给当天到期的加个小标记。卡点提醒：过期和未完成的组合状态有几种，先在纸上列全再动手，别写到一半发现漏了"已过期且已完成"这种组合。

练习二：分类与筛选。目标：待办分几个自定义分类（工作、生活、学习……），顶部一排分类签，点谁筛谁。提示：模型加 category 字段，list() 加 WHERE 条件参数；筛选状态用一个 @State 存，切换分类就带着条件回查。卡点提醒：筛选之后的空状态要区分"这个分类还没有待办"和"这个分类的都做完了"两种；另外统计卡片要不要跟着筛选走，想清楚再写——统计口径一变，代码结构会跟着变。

练习三：撤销删除。目标：点删除后条目立刻消失，但底部浮出一条"已删除，撤销"的提示，几秒内可撤。提示：两条路自己选——内存暂存法（删除的整条数据先存内存，撤销时重新 add 回去，注意 id 会变，键要跟着处理）或软删除法（表加 deleted 标记，所有查询带 WHERE，定时真删）。卡点提醒：软删除法会让本章所有查询都要过一道"没删的"，牵一发动全身，选之前想清楚；计时器的清理也别忘，提示条没消失时又删了一条，计时要不要重置？

练习四：导出与备份。目标：一键把全部待办导出成一个 JSON 文件，能存到手机目录或用系统分享发给自己；顺手想想导入怎么做。提示：list() 的结果序列化成 JSON 字符串，写文件用官方的文件能力（具体接口以官方文档为准）。卡点提醒：导出的是明文数据，里面可能有不想给人看的待办——分享对象选清楚；导入要做字段校验，别让一个手改坏的 JSON 把整库写花。

练习五：桌面卡片。目标：桌面放一张小卡片，显示"今日还有几件没做"，点卡片直达应用。提示：这是官方"服务卡片"（ArkTS 卡片）能力的地盘，跟着官方文档的向导走一遍创建流程；数据来源就用第六节的统计接口。卡点提醒：卡片和应用主体是两个运行环境，数据的刷新节奏、更新时机都有官方约定，别想当然地"卡片自己查库"——先把文档里的说明读完，再动第一行代码。这道题做完，你对"应用不止一个界面"的理解会上一个台阶。

五道题的共同起手式都是同一句：先改模型和数据库，再改数据层方法，最后改界面。如果你发现自己想反过来先改界面，说明分层的习惯还没长进手上，回到第一节重读一遍设计意图，比硬写更省时间。

练习的验收线：做到什么程度算"做完了"

五道题各画一条完成线，防止练习做成烂尾楼。练习一的完成线：设了截止时间的条目。过期自动标红，并且杀掉应用重开后仍然正确——注意"重开后"三个字，只看当前会话等于没做迁移；练习二的完成线：切换分类之后，列表、空状态、统计卡片三者的口径一致，不会出现列表空了统计还在涨的分裂场面；练习三的完成线：撤销窗口期内杀掉应用再重开，数据状态符合你选的方案：软删除的数据还在，内存暂存的就真没了，两条路各有各的对。

练习四的完成线：导出的文件拿到别的设备或电脑上能打开、字段完整，在自己应用里能读回来不算数，那叫自产自销；练习五的完成线：卡片上显示的数字和杀掉应用前的实际状态一致，点卡片能直达列表页，而不是重新冷启动一遍。为什么所有标准都卡在"跨场景还成立"？因为本地应用的敌人就是时间：会话切换、设备切换、版本切换，练习练的，正是你的应用在这三种切换面前不变脸的能力。

每道题做完，按完成线自测一遍，不过线就继续修。你会发现大部分返工都发生在数据层，这是好事，说明你已经习惯把复杂度收进该收的层里，界面只是被动地展示结果。这个信号出现的时候，本章教你的分层，就真的归你了。

十、项目复盘：分层思想，与记账本的对照

应用做完了，最后一节不写代码，做复盘——把这一章练到的东西从"操作"提炼成"方法"，下一个项目才能做得更快。

先盘结构。这个应用总共三层：模型（Todo，纯数据定义）、数据层（TodoDb，增删改查与统计）、界面层（@State 加 build，只读状态、发起动作）。每层的职责一句话说清：模型定义"数据长什么样"，数据层负责"数据怎么存怎么取"，界面层负责"长什么样、怎么响应"。自测分层是否干净有个土办法：换掉任何一层，看另外两层要不要动。把 RelationalStore 换成 Preferences，界面不该动一行；把 List 换成网格，数据层不该动一行。动了，说明职责有渗漏，回头把渗漏的地方收回来。

再盘章法。回看这一章的每一步：定模型、写数据层、搭列表、补交互、做打磨，顺序从来没变过：先把数据的"地基"打好，再往上盖界面。这不是巧合，是你第二次走这条路：第 65 章 iOS 篇的记账本，同样的开局，先定账目模型，再封数据层，最后搭界面；安卓篇的记账本，还是这个顺序。把三个平台各写一遍同类应用，你会攒出一张自己的概念对照表：

概念鸿蒙（本章）在别的平台叫什么（大致对应）
界面状态源@State，一变就重绘声明式 UI 的状态属性，思想同源
列表渲染与复用键ForEach + 键生成器各家列表组件都有"键/标识"概念
本地数据库RelationalStore（SQLite）移动端本地库多数也建在 SQLite 上
数据层封装TodoDb 类，UI 不碰 SQL换个名字的同一个思想

这张表想说明的事只有一件：语法三个月就换一茬，概念十年不动。第 65 章你在 iOS 里学的"状态驱动刷新"，和本章 @State 的道理一模一样，数据变了界面自己重画，人只管改数据。以后再遇到新平台、新框架，你找的不再是"这的 ForEach 叫什么"，而是"这的状态、列表、本地库各是哪个"，问题对了，答案就快了。

顺手清三误区。误区一："教程跑通就算学会了"：教程跑通只说明你能照做，合上教程给应用加一个新功能才是学会了，第九节的五道题就是干这个的。误区二："分层是大项目才需要的"，恰恰相反，分层是在小项目上练出来的习惯，等项目大到"需要"分层时你才会用，黄花菜都凉了；两三百行的项目练手，正是练分层的好时候。误区三："深色模式和读屏是锦上添花，以后有空再说"，它们不是花，是普通用户每天都在过的日子，"以后再说"的项目清单里，它们通常说的日子永远不会来。

复盘落笔：给下一章的自己留一页

复盘的产出别只留在脑子里，也别只留在聊天记录里。翻开你的开发备忘录，从第 75 章搭环境起就该记的那本，给本章留一页，写四样东西。第一，三条你真正学会的方法，每条配一个自己的例子："改库必回查"配你那次列表不刷新，"键用主键"配小周的牛奶，"初始化归生命周期"配 build 刷屏那次。方法配上自己的例子，才算真的长在身上。第二，三次翻车现场，各一句话：现象、原因、修复动作，三栏写完，以后再遇到同类报错，你的手会比脑子先动。

第三，练习清单。从第九节圈出你最想做的两道，写上打算动手的日期，没有日期的"想做"大多不会发生，有日期的才叫计划。第四，一行疑问。你在本章一定攒下了没答上的问题：提醒怎么做？为什么数据库要记版本号？卡片和应用怎么共享数据？原样写下来，带进下一章。带着问题去学新内容，学到的至少多一倍，这是所有学得快的人共用的小秘密，不值钱，但极少有人真的在用。

这一页为什么值得花二十分钟？因为教程是地图，你写下的这页才是你的旅行日志。半年后你做第二个、第三个项目，卡住的时候翻自己的日志，比翻任何目录都快；你会惊讶地发现，那些坑你真的都趟过一遍：这个发现本身就是底气：上一个项目你走通了，这一个也走得了。开发备忘录从今天起会越来越厚，它和代码一样是你手里的资产，而且是你亲手攒下的那部分。

最后往前面看一步。下一章会把这个应用接上网络，数据从"只存在手机里"变成"能上传、能同步"。你会发现那一章的活儿轻很多：界面还是这个界面，数据层多了一种"远程实现"，网络请求不过是数据层的又一个"可替换部件"。第 74 章的应用骨架、本章的分层数据层，到那时才开始显出全部价值，骨架和分层不是为了现在好看，是为了将来能扩。应用是长出来的，不是一次画出来的；你现在已经把第一块骨头长齐了。

十一、高频问题快答

这一节是门诊之后的候诊室：十二个真实学友问过的高频问题，答案都不长，但每个都对着一个具体的纠结。带着自己的问题来对号；没对上的也别干等，动手试一遍往往比等答案更快。

问：我完全没学过 ArkTS，能不能直接跳到这一章做项目？

答：能试，但会磕绊。这个项目用到的语言特性在第 72 章都有对应小节，界面组件在第 73 章，应用骨架在第 74 章。建议先花半小时把第 72 章的接口、类和 async/await 过一遍再回来，效率高得多。跟着敲完整章本身就是学语言最快的路，只是报错的时候别怀疑自己，报错是这门课的助教。

问：为什么用 RelationalStore 这么"重"的东西？存几条待办，用 Preferences 不行吗？

答：行，而且这条替换路径第一节就预留好了：换实现不动界面，这正是分层的红利。但选 RelationalStore 有两个更硬的理由：一是待办天然要排序、筛选、统计，SQL 一句话的事，Preferences 存 JSON 得整包读进内存自己筛；二是关系型库是这个领域的通用技能，学一次，三个平台都认。数据量小不是问题，查询需求才是选型的分水岭。

问：预览器里能跑这个项目吗？数据存在哪里？

答：界面布局用预览器看很方便，但数据库这类系统能力在预览器里能不能完整跑起来，随工具版本而变，以官方文档为准。稳妥的分工是：预览器调布局，模拟器或真机跑全功能。顺手记住前面说过的一条：模拟器、真机、预览器各自的存储互不相通，你在 A 设备上添加的待办，B 设备上当然看不见，这不是 bug，是"本地存储"四个字的应有之义。

问：ForEach 和 LazyForEach 有什么区别？我要不要现在就换成 LazyForEach？

答：ForEach 把列表数据一次全渲染，LazyForEach 只渲染屏幕附近的那一小段，数据量大的时候差距才明显。你现在几十条待办，ForEach 毫无压力，换了也看不出区别。什么时候换？等你的列表真的卡了，或者你练习五导入了上千条历史数据的时候。过早优化和过晚优化一样伤项目，判断标准就是实测卡不卡。

问：@State、@Prop、@Link、@Provide……装饰器一大堆，这个项目到底要用哪几个？

答：这一章只用 @State 就够了，todos 和 input 都待在同一个组件里，不需要跨组件传递。等你把界面拆成多个子组件（做完第九节的练习自然会拆），父子组件要传值了，再去查官方文档的状态管理章节，把 @Prop、@Link 按需请进来。装饰器不需要背表，用到哪个查哪个，查三次自然就记住了。

问：新增成功之后，要不要弹一个"添加成功"的提示？

答：多数时候不用。列表立刻多出一行。这本身就是最直接的反馈，再来一个提示反而吵。提示留给"结果看不见"的场景：添加被防重复拦下、导出完成、删除后撤销窗口关闭。到处弹提示和到处弹确认框是同一种病：不相信自己的界面在说话。界面能说清的事，别麻烦吐司。

问：Checkbox 的 onChange 会不会在列表刷新时被误触发？我怕写出死循环。

答：方向想得对，但机制上不用担心：onChange 只响应用户的交互，代码里用 select 做回显不触发它（以官方文档为准）。真正会咬人的地方还是键生成器——键不稳，整行被重建，回显状态错乱，看起来就像"onChange 乱触发"。把键修成唯一 id，这类玄学基本绝迹。排错的力气花在键上，别花在怀疑生命周期上。

问：能不能不用数据库，直接把待办存成 JSON 文件？

答：能，数据层换一个实现就行，界面一行不动，建议真做一版对比体会。但要心里有数：JSON 文件适合"整体读写、量小、结构简单"的场景；一旦要做排序、筛选、统计、部分更新，手写文件逻辑很快会演变成一场在内存里模拟 SQL 的行为艺术。做完两版对比，你对"什么时候该上数据库"的手感就建立起来了，这比看任何选型文章都管用。

问：什么时候值得给这个应用加云同步？

答：当你真的开始"出门在手机上记一条，回家想在平板上勾掉"的时候。技术上这是给数据层再长一个远程实现，外加账号体系，工程量是本章的三五倍起步。练手阶段更划算的做法是先做导出备份（练习四）：手动同步虽然笨，但它用最小的成本回答一个重要问题，你到底是真的需要同步，还是只是觉得同步听起来厉害。需求先用笨办法验证，再上重工程，这个顺序能帮你省掉大量白干的活。

问：Index.ets 越写越长，几百行了，怎么拆？

答：按第 37 章的思路下三刀。第一刀，独立界面拆出去：对话框已经是独立的 view 目录组件了，列表行也可以拆成单独的行组件；第二刀，数据操作全部收进 TodoDb，页面里不许出现 SQL；第三刀，工具函数（校验、格式化时间）放进 utils。拆完的主页面回到一百行上下，每个零件在目录里各就各位，改哪儿找哪儿。拆的时机不用等"太长了"才动手——一个文件里出现第二种职责时就可以拆了。

问：升级 SDK 之后项目突然报错，是不是我代码写错了？

答：先别急着改。读报错——接口改名、废弃这些事，编译器会明说（第五节病号五的 getContext 废弃告警就是标准样本），给出的一键替换多数可靠。改完跑一遍第七节那三条单元测试，绿了再继续开发。升级适配是开发者的日常功课，报错不可怕；可怕的是不看报错内容，直接上网搜"玄学修复"把代码越改越乱。

问：做完这个项目，下一步做什么最好？

答：两条路。近路：跟着下一章把这个应用接上网络，亲眼看看"数据层多一个远程实现"是什么手感。远路：给自己挑一个真实需求，记账、健身打卡、读书清单都行：用本章的套路从零做一遍。真实需求会逼你回答教程不会问的问题：这个字段到底要不要存、这个场景到底要不要提示、按钮到底放不放。回答完这些，你就从"会做项目"走到"会做产品"了。

十二、一次完整的排错实录：从"列表不刷新"到修好

门诊给了症状对照表，这里再给你一次完整的实战推演：把第八节的三条经验串成一次真实的排错过程。

翻车现场

周日晚上十点，你在自己的待办应用里收尾。添加一条测试数据，输入框清空了，列表纹丝不动。杀掉应用重开，数据又在——刚才其实添加成功了，只是列表没刷新。

"添加完输入框清空了，列表却没多一条"

场景来源：全书通用场景（非特定读者）

怎么办：先二分——用日志把 list() 的结果长度打出来（日志接口的用法以官方文档为准）。日志里躺着两条数据，界面上只有一条：库是好的，问题在界面侧，接下来只需要查 @State 和 ForEach。再往细看，发现键生成器写的是 t.title：下午测防重复时把查重逻辑注释掉了，又手滑加了两条同名的"买牛奶"，键撞了，框架认为"数据没变化"，重绘被跳过。改回 t.id.toString()，列表当场活过来。

第一幕：二分定位。先别改代码，先问一句：是真没插进去，还是插进去了没刷新？这一刀把问题切成两半。用日志把 list() 的结果长度打出来（日志接口的用法以官方文档为准）：日志里躺着两条数据，界面上只有一条——库是好的，问题在界面侧。这一步的价值不在找到答案，在于排除了一半的可能：接下来你只需要查 @State 和 ForEach，不用去翻数据层。

先二分。

第二幕：锁定真凶。刷新代码在（this.todos = await this.db.list()，整体赋值没毛病），再往细看键生成器——写的是 t.title。你这才想起来，下午测防重复功能时把查重逻辑注释掉了，又手滑加了两条一模一样标题的"买牛奶"。两条数据的键撞了，框架认为"数据没变化"，重绘被跳过。改回 t.id.toString()，列表当场活过来。你盯着屏幕上那两条重名的牛奶，又好气又好笑——下午为省事注释掉的查重，晚上变成了排错一小时的伏笔。

第三幕：修复验证。改完别急着合上电脑。把键生成器恢复成 id 之后，把第七节那三条单元测试跑一遍：新增加一、勾选翻转、删光归零，全绿。再把查重逻辑从注释里捞回来，重复添加被拦下的提示也正常。到这里才算修完——修好的定义不是"我看着好了"，是"测试证明它好了"。

修完必须复测。

这次实录值得沉淀三条心法。第一，排错先二分。库还是界面、数据还是渲染，先切一刀再深入，别两头同时找。第二，打印优先于猜测。一行日志的一分钟，胜过盯着代码发呆的十分钟。第三，修完必须复测。没有测试兜底的"修好了"，只是"这次没复现"。这三条不只适用于本章的项目——你以后写的每一个应用。排错的路径都是这一条。

十三、三种学习节奏，三种走法

同一个项目，不同的人时间结构完全不同。对号入座，领走适合你的那份计划。

碎片时间党：两周走完，每次十五分钟

你的时间碎在通勤、午休和睡前的缝隙里，那就把本章也切碎：通勤时段读正文、记划线句，晚上固定十五分钟动手，每次只啃一个小节，做完即停。具体排法：前三天走第一节（数据层），中间四天走第二节（列表页四件事），再四天走第三、四节（输入与删除），最后几天吃下编辑、统计和打磨。两周收工。这类节奏的敌人是"断了就再也没捡起来"，对策是给自己定一条铁律：十五分钟到了就停，哪怕正写到一半。留个尾巴，下次开工更快。

周末突击党：一次三小时，四段分配

你适合一口气打通，但要防"抄完就忘"。三小时这样切：第一段四十五分钟，照抄第一、二节，跑通骨架，注意是照抄，别发挥，肌肉记忆靠手不在靠眼；第二段四十五分钟。弹窗、校验、防重复，把自己的输入体验调顺；第三段四十五分钟，编辑加优先级，把表结构迁移亲手踩一遍；最后四十五分钟，统计卡片加三条测试，收尾验证。全程只在每段结束时报一次错，中途遇到小报错先记在备忘录，别让排错打断整体节奏，留到段末集中处理。

带着真实需求来的人：改造优先

你不是来"学教程"的，你是来把它改造成自己的应用的：健身打卡也好、学习清单也好。给你的路线不同：第一、二节照抄跑通（地基不能歪），从第三节开始就换成你的模型和你的文案，每学完一节问一句"这一节的东西能替我省掉什么事"。你的风险是需求膨胀：做着做着想把提醒、统计图表、多设备同步全加上。守住一条线，增删改查加持久化的闭环没跑稳之前，不加新菜。真需求是燃料，也可能是火灾。区分标准就是你此刻的闭环稳不稳。

十五、术语小抄：本章名词一页通

本章新名词比前几章都密，收进一张表，忘了回来查。每条解释都按"它是干什么的"来写，不背定义，理解用途。

一句话记牢：先跑通闭环，再换好零件

新项目别追求一步到位：先用最笨的办法把"输入 → 状态 → 界面 → 存储"闭环跑通，然后一次换一个零件：弹窗换掉行内输入、滑动换掉行内按钮、资源色换掉写死的颜色。每一刀都小到随时能停，每一步应用都保持能用。这就是本章的全部章法。

  • 把「界面 / 状态 / 存储」拆开练熟，下一章加网络只是多接一层
